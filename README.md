# LiveCord 桌面版（Windows）

[LiveCord](https://live.felisnyan.com) 的 Windows 桌面软件：聊天 + 直播。和网页版是同一个站、同一套账号，互相能聊天、能看对方的直播。

下载（1.0.2 起有两个）：

- **安装器**（约 0.4 MB，安装时选版本）：<https://github.com/Felis-desuwa/livecord-desktop/releases/latest/download/LiveCord-Installer.exe>
- **完整版安装包**（约 100 MB，直接装完整版）：<https://github.com/Felis-desuwa/livecord-desktop/releases/latest/download/LiveCord-Setup.exe>

（安装包没有代码签名，Windows 可能提示"未知发布者"，点"更多信息 → 仍要运行"。装到当前用户目录，不需要管理员权限。）

| | 完整版（推荐） | 轻量版（试验） |
|---|---|---|
| 浏览器内核 | 自带（Electron 45 / Chromium 156，版本固定） | 用系统里的 WebView2（Edge 内核，随系统自动更新） |
| 下载 / 装好后占用 | 约 100 MB / 280 MB | 约 0.4 MB / 不到 1 MB |
| 内存、CPU | 见下面的实测 | 不比完整版少（空闲时实测 420 MB，完整版 370 MB） |
| 直播 | 各项数据都是在它上面实测的 | 功能相同；差别和风险见「轻量版」一节 |

## 和网页版比多了什么

| | 网页版 | 桌面版 |
|---|---|---|
| 边打游戏边播 1440p | 抓屏只有 50～60 帧（实测 52） | 稳定 120 帧（实测 119.7，最低 116） |
| 只播游戏的声音、不带 Discord | 靠浏览器的窗口音频，不可靠 | 系统级按进程采集，选哪个程序就只有哪个程序 |
| HDR 屏幕 | 画面发灰，靠估计去校正 | 按系统的"SDR 内容亮度"精确换算 |
| 240 帧 | 做不到 | 可以选（试验；实际帧数取决于游戏自己的帧数） |
| AV1 | 软件编码，1440p 约 55 帧 | 显卡编码（1.0.1 起，试验；显卡要有 AV1 硬件编码器，RTX 40 系及以后 / Intel Arc / RX 7000 等） |
| 网络差的观众 | 只能卡 | 同时发一路 720p 流畅档，服务器按每个观众的下行带宽自动切 |
| 开播时软件自己占的 CPU（1440p，游戏满载） | 1.8 个核 / 52 帧 | 0.9 个核 / 120 帧 |

提醒方面：**没有任何主动提醒**（没有系统通知、托盘气泡、任务栏闪烁、角标）。只有三种音效：有人进入 / 离开你所在的直播（你在播或你在看），以及开播（别人开播；你自己的画面推上去时也响一声）。设置里可以关、可以调音量。

## 实测占用

测试机：Ultra 7 270K（24 线程）+ RTX 5070 Ti，2560×1440 HDR 240Hz，Windows 11。开播数据都是 Deadlock 正在运行（显卡占用 95% 以上）时测的，上传到本机的测试服务器。CPU 是软件所有进程（界面、网络、显卡进程、两个助手）加起来占"一个核"的百分比。

| 状态 | 采集 / 编码帧率 | 每帧编码 | CPU | 内存（工作集 / 独占） | 显卡（3D / 编码器） | 显存 |
|---|---|---|---|---|---|---|
| 空闲（已登录，窗口开着） | — | — | 1%（整机 0.04%） | 370 / 182 MB | 0 / 0 | 31 MB |
| 流畅：1080p 60 帧 8 Mbps | 60 / 60 | 2.1 ms | 44%（整机 1.8%） | 755 / 513 MB | 0.9% / 9.8% | 205 MB |
| 高清：1440p 60 帧 20 Mbps + 流畅档 | 60 / 60 | 3.6 ms | 59%（整机 2.5%） | 775 / 570 MB | 1.1% / 19% | 252 MB |
| 1440p 120 帧 40 Mbps + 流畅档（「极致」预设现在是 60 Mbps） | 119.7 / 119.8（最低 116） | 3.6 ms | 89%（整机 3.7%） | 760 / 553 MB | 1.5% / 35% | 251 MB |

"编码器"那一栏是显卡上专门的编码电路（NVENC），不和游戏抢渲染资源；和游戏抢的"3D"部分只有 1% 左右。CPU 里大头是把码流发出去（加密 + 发包），和码率成正比。

## 它是怎么做的

窗口直接加载线上网站（界面随网站更新，不用重装）。这个壳只做浏览器做不到的三件事：

1. **画面**（`native/lc-capture.cpp`）：用 Windows Graphics Capture 直接拿显存里的画面，着色器里做缩放、HDR→SDR、转 NV12，交给显卡的 H.264 编码器（Media Foundation）。全程不读回内存。输出的是成品码流。
   - 为什么不用内核自带的抓屏和编码：实测它在 HDR 屏上每抓一帧要 8～9 毫秒，而且两次抓取的间隔不能小于单次耗时的两倍，所以最多 50～60 帧；把显存里的画面直接交给内核的编码器，它每帧还要同步读回一次，约 84 帧、占 1.7 个核。
   - 码流怎么进 WebRTC：发送端编一路极小的纯色"占位"画面，用编码后变换（`RTCRtpScriptTransform`，`public/desktop-vworker.js`）把内容换成真正的码流。打包、重传、带宽估计仍由浏览器做。
2. **声音**（`native/lc-audio.cpp`）：WASAPI 的按进程回环采集，可以"只要这个程序"或"除了这个程序都要"。PCM 经 MessagePort 直接进页面的 AudioWorklet。
3. **内核参数**：关掉 D3D12 编码接口（走浏览器编码的后备路径时用 MediaFoundation，游戏满载下不排队）。

原生采集起不来时（没有对应的硬件编码器、系统太旧）或者选了 VP9，自动退回浏览器自带的采集和编码，控制条上会显示"浏览器采集"。

### AV1（1.0.1 起，试验）

画质里把编码选成 AV1 即可，同样码率比 H.264 清晰。注意：

- 观众的设备要能解 AV1：电脑上的 Chrome / Edge / Firefox 都行；iPhone 要 15 Pro 及以后，更早的看不了
- 没有流畅档副路（只有一路）
- 实现上和 H.264 不一样：转发服务器认 AV1 的关键帧只看"依赖描述"扩展头，而这个扩展头是照着占位帧写的，所以占位帧和真帧必须严格对齐
  （一帧不丢、关键帧位置对上），见 `public/desktop-vworker.js` 里的"严格模式"
- 高帧率时编码器自动用最快档：AV1 在 1440p 约 160 帧以上、4K 约 72 帧以上时，编码器的质量 / 速度档位从中间档改成最快档。原因是显卡被游戏占满时，中间档每帧要 5.3 毫秒，1440p 240 帧只编得出 180 帧（最快档 4.1 毫秒，235 帧）。画质代价：用游戏录像在显卡 AV1 编码器的最快 / 中间预设之间对比，同码率 VMAF 低约 1 分。这是用合成的显卡负载测的，真实游戏下还没测
- 本机实测（没开游戏，测试画面）：3840×2160 / 120 帧，编码 119.9 帧、每帧 4.9 毫秒，观众端解码约 119 帧。**边打游戏时的表现还没测**

### 按观众减帧（1.0.3 起，AV1 高帧率时）

高帧率直播遇到解码能力一般的观众，画面会像慢放：收到的帧比解得出来的多，帧在缓冲里越排越久，攒满了再跳一下。后面的帧要参考前面的，播放器不能自己挑着丢帧。

1.0.3 起，AV1 在 100 帧以上时按**时间分层**编码（`lc-capture --tl 3`）：帧按 0-2-1-2 排成三层，高层的帧不被低层参考，可以整层不发。转发服务器按每位观众的情况只发低几层——同一路画面，有人收 240 帧，有人收 120 或 60 帧，分辨率不变、速度正常。不多编一路，上传不增加。

- 观众端自动选：不收比屏幕刷新率高太多的帧率（60Hz 的屏看 240 帧只收 60 帧）；解码跟不上时自动降一层。画面上的「帧率」按钮可以手动固定。
- 实现：占位帧也声明同样的分层（`scalabilityMode: L1T3`），服务器照占位帧的"依赖描述"扩展头挑层，所以真帧必须放进同一层的名额里（`public/desktop-vworker.js`）。两边都在关键帧之后从第 0 层重新数；对不上时（比如助手重启过）让占位编码器重出关键帧，从头对齐。
- 本机实测（测试画面）：1440p 240 帧，单核软件解码的观众从"落后 1.1 秒、越拖越久"变成自动降到 120 帧再降到 60 帧后稳定，等待 9 毫秒；编码器每帧耗时不变（2.28 对 2.33 毫秒）；直播中改分辨率、帧率、编码时分层跟着开关，层保持对齐。
- 还没有的：H.264 没接分层（它走的是不带扩展头的普通模式，解不动的观众仍然是切到 720p 30 帧的流畅档）；真实游戏画面、显卡满载、非 NVIDIA 显卡、Firefox / Safari / iPhone 观众都没测。

## 轻量版（1.0.2 起，试验）

`lite/` 目录：一个 400 KB 的原生外壳（`lc-lite.cpp`），不带浏览器内核，用系统里的 WebView2。画面和声音还是那两个助手，网站的界面代码一行没为它改 —— 外壳往页面里注入一段脚本（`lite/shim.js`），提供和完整版一样的 `window.lcDesktop` 接口。

和完整版不一样的地方：

- **数据通道**：WebView2 的外壳和页面之间只能互发文字。码流、声音、预览放在一块共享内存里（外壳写、页面只读），外壳每写一段发一条很短的通知，页面拷出来再交给 Worker / AudioWorklet。所以数据**要经过页面主线程**（完整版是主进程直接送进 Worker 的）。
- **预览**：没有共享纹理接口，改成助手把小画面读回内存（`lc-capture --pvraw 1`，640 宽、每秒 20 帧）。
- **标题栏**：用系统自己的。
- **退回浏览器采集时**（选了 VP9，或原生采集起不来）：弹的是内核自己的共享选择框，开播面板里选的来源不起作用。

本机实测（WebView2 158，测试画面，没开游戏，本机转发服务器 + 无窗口 Chrome 当观众）：

| | 完整版 | 轻量版 |
|---|---|---|
| H.264 1440p 120 帧 60 Mbps + 流畅档 | 编码 120 帧，观众 120 帧 | 编码 120 帧，观众 120 帧 |
| AV1 1440p 120 帧 40 Mbps | 119.9 帧 | 120 帧 |
| 码流从助手到 Worker 的额外延迟 | — | 请求关键帧到收到平均 12 毫秒，最长 33 毫秒 |
| 稳定直播时发送端到服务器的丢包 | 0 | 0 |
| 新观众进来的那一下，发送端到服务器的丢包重传 | 0 包 | 每次 24～91 包（都重传成功） |
| 新观众的首帧时间（约 25 次） | 都是 1.3 秒 | 多数 1.3 秒，2 次 3 秒（关键帧缺包，等了服务器 2 秒的节流） |
| 空闲内存 | 370 MB | 420 MB |

**风险**（安装器里也写了）：

- 内核版本不归软件管。高帧率直播靠的那几条规则（见 `public/desktop-vworker.js` 开头）是在固定版本上实测出来的，系统更新 WebView2 之后可能失效，而且事先拦不住。
- 上表里"新观众进来时的丢包"是架构带来的：数据经过页面主线程，到达的节奏不如完整版均匀。真实网络、真实游戏负载下没测过。
- 没测过的：边打游戏时的表现、长时间直播、全屏看别人直播、Windows 10、没有 WebView2 运行时的电脑（外壳会提示改装完整版）。

## 开发

```
npm install
npm run build:native     # 编译两个助手到 bin\（需要 Visual Studio 的 C++ 工具集）
npm run dev              # 连本地的网站实例 http://localhost:3187
npm start                # 连线上
npm run dist             # 打完整版安装包到 dist\LiveCord-Setup.exe

lite\build.cmd           # 编译轻量版外壳到 lite\out\LiveCordLite.exe
                         #（先把微软的 Microsoft.Web.WebView2 NuGet 包解到 lite\webview2sdk：要 build\native\include 和 build\native\x64）
node lite\make-installer.js   # 打「可选版本」的安装器到 dist\LiveCord-Installer.exe（用 electron-builder 缓存里的 NSIS，先跑过一次 npm run dist）
```

- 轻量版的启动参数：`--lc-url=`、`--lc-hidden`（窗口放到屏幕外）、`--lc-noactivate`（正常显示但不抢焦点）、`--remote-debugging-port=`。数据目录 `%LOCALAPPDATA%\LiveCord Lite`（环境变量 `LC_USER_DATA` 可改）。页面里 `lcDesktop._lite()` 能看数据通道的统计。
- 安装器：选完整版时是从 GitHub 下载 `LiveCord-Setup.exe` 再运行；静默安装（`/S`）装的是轻量版，加 `/NORUN` 装完不打开。

- 界面代码在网站那边：`public/desktop.js`、`public/desktop.css`、`public/desktop-vworker.js`、`public/desktop-pcm.js`（只有桌面版会加载）。
- `npm run dist` 要在路径不太长的目录里跑（安装包工具打不开超长路径）。
- 启动参数 `--lc-url=http://localhost:端口` 只认本机地址。`--lc-hidden` 不显示窗口（自动化测试用）。
- 助手可以单独跑：`bin\lc-audio.exe list`，`bin\lc-capture.exe <父进程号> monitor <x> <y> --fps 120 --bitrate 40000000`（协议见源码开头的注释）。

## 已知的限制

- 1440p / 120 帧的直播，新观众刚进来时可能先卡一两秒才出画面（解码器启动慢了，等下一个关键帧；服务器对同一场直播的关键帧请求有 2 秒的节流）。之后正常。
- AV1 是试验性的：只在没开游戏时测过，观众设备的兼容面也比 H.264 窄
- 240 帧是试验性的：编码没问题，但帧数取决于游戏本身（实测游戏 185 帧时就是 185 帧），而且 1440p 240 帧超出了多数手机的解码能力，建议配 1080p。
- 画面完全不动时每秒只发 2 帧（省流量），一动就恢复。
- 采集的窗口最小化后没有新画面（系统不给）。
